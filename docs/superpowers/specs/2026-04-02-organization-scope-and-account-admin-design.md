# 机构隔离与账号审批扩展设计

## 背景

当前账号体系已经支持多机构注册、机构审批与邀请码加入，但业务数据仍存在“机构边界不完整”的问题：

- 机构负责人在 `账号审批` 页面能看到其他机构的成员
- 新机构账号能在多个 Tab 中看到 `星润Starain` 的历史数据
- 超级管理员当前只能处理“待审批机构申请”，缺少“已注册机构列表”视角
- `账号审批` 页面还不能直接编辑成员姓名

这说明系统目前只有“账号属于机构”的概念，但核心业务数据与查询权限尚未全部按机构收口。

## 目标

- 所有机构用户默认只能看到自己机构的数据
- 超级管理员可以跨机构查看与管理全部机构
- 历史业务数据统一归属到 `星润Starain`
- `账号审批` 页面支持编辑成员姓名
- 超级管理员在审批页可以看到“已注册机构”而不只是待审批申请

## 非目标

- 本轮不开放在审批页修改成员账号
- 本轮不做复杂的历史数据自动归属推断
- 本轮不重构整套权限模型名称与角色定义

## 决策

### 1. 历史数据归属

历史上已经存在的业务数据全部迁移归属到 `星润Starain`。

理由：

- 风险最低，不会把历史数据误分给新机构
- 迁移规则简单、可验证
- 与当前业务事实更接近，系统最早就是单机构使用

### 2. 数据隔离原则

- `super_owner`：可查看和管理所有机构及全部机构数据
- `owner` / `admin` / `member`：只能访问自己 `organization_id` 下的数据
- 前端 Tab 隐藏不是安全边界，必须由后端接口强制执行机构过滤与归属校验

### 3. 审批页成员编辑范围

- 本轮仅允许编辑“姓名（display_name）”
- 不允许在本轮修改“账号（username）”
- `super_owner` 可编辑所有非自己超级管理员账号的姓名
- `owner` 可编辑自己机构内 `admin/member` 的姓名
- `owner` 先不允许编辑同机构 `owner` 的姓名，避免机构负责人之间互改资料

## 数据模型设计

### 需要补齐机构归属的数据

以下核心业务数据需要能够明确归属于某个机构：

- `classes`
- `lessons`
- `consultations` 记录
- `registration_requests`
- 需要按机构展示的教学绑定摘要与相关派生查询

### 迁移策略

#### classes

- 为 `classes` 增加 `organization_id`
- 历史 `classes` 全部写入 `星润Starain` 的 `organization_id`
- 后续新建班级时，从当前登录用户继承 `organization_id`

#### lessons

- 为 `lessons` 增加 `organization_id`
- 历史 `lessons` 全部写入 `星润Starain`
- 后续新建课节时：
  - 若已选择班级，则以班级所属机构为准
  - 若无班级，则继承当前登录用户机构

#### consultations

当前咨询记录使用 CSV 存储，缺少机构归属能力。本轮将咨询记录迁移为 SQLite 表并增加 `organization_id`。

- 新建 `consultations` 表，字段对齐现有 CSV 结构并增加 `organization_id`
- 首次迁移时把现有 CSV 全部导入数据库并归属到 `星润Starain`
- 导入完成后，运行时查询改为读 SQLite，不再以 CSV 作为主存储
- 保留 CSV 只作为一次性迁移来源，不再作为写入目标

### registration_requests

`registration_requests` 已有 `organization_id`，本轮不需要补字段，但需要把读取与审批行为按操作人机构进一步收口。

## 后端设计

### 新增/调整的核心查询能力

新增按机构范围查询的方法，而不是继续复用全量方法：

- `list_users_for_actor(actor_user)`
- `list_registration_requests_for_actor(actor_user, status='pending')`
- `list_classes_for_actor(actor_user)`
- `list_lessons_for_actor(actor_user, ...)`
- `list_consultations_for_actor(actor_user, query='')`
- `list_organizations()` 供超级管理员查看已注册机构

规则：

- 若 `actor_user.role == 'super_owner'`，返回全量
- 否则按 `actor_user.organization_id` 过滤

### 详情与写操作校验

除列表接口外，详情与写操作也必须校验机构归属：

- 读取某个班级/课节/咨询记录时，若不属于当前机构则返回 `404`
- 更新、删除某个班级/课节/咨询记录时，若不属于当前机构则返回 `404` 或 `403`
- 给成员分班、改角色、改姓名时，目标用户必须属于可管理范围

### 机构列表接口

为超级管理员增加“已注册机构列表”接口：

- `GET /api/admin/organizations`

返回内容至少包含：

- `id`
- `name`
- 成员数
- 负责人数量
- 班级数
- 课节数
- 创建时间

该接口仅 `super_owner` 可访问。

### 审批页编辑姓名接口

新增或扩展后台成员资料更新接口：

- 推荐新增 `PUT /api/admin/users/<user_id>/profile`

请求体：

```json
{
  "display_name": "新的姓名"
}
```

规则：

- `display_name` 必填且去除首尾空格后不能为空
- `super_owner` 不可通过此接口修改自己的显示名
- `owner` 仅可编辑本机构 `admin/member`
- 超出权限范围时返回 `403`
- 目标用户不存在或不属于可管理范围时返回 `404`

## 前端设计

### 1. 账号审批页成员列表

成员列表继续保留当前卡片式布局，但每张卡片新增一个“编辑姓名”入口：

- 点击后展开轻量编辑态或小弹层
- 只展示一个姓名输入框
- 保存成功后局部更新该成员卡片
- 失败时在当前页显示错误提示

### 2. 超级管理员机构列表

在 `ApprovalPage` 中，`机构开通审批` 区块下方新增“已注册机构”列表：

- 仅超级管理员可见
- 显示机构名称、成员数、负责人数量、班级数、课节数
- 首版本先做只读，不强行加入复杂操作

### 3. 各业务页行为

前端不再假设“owner/admin 能看全部”，所有页面直接使用后端返回的已过滤数据：

- 课程/班级
- 咨询记录
- 智能错题
- 账号审批
- 教学绑定摘要

这意味着前端侧只需要配合新的接口数据，不在前端自行拼机构隔离逻辑。

## 迁移步骤

1. 为 `classes`、`lessons` 增加 `organization_id`
2. 创建 `consultations` 表并将历史 CSV 导入 SQLite，全部归属 `星润Starain`
3. 回填历史 `classes`、`lessons` 为 `星润Starain`
4. 新增按 actor 过滤的后端查询函数
5. 把相关 API 切到按机构过滤的新查询
6. 新增超级管理员机构列表接口
7. 新增审批页编辑姓名接口
8. 前端接入“已注册机构列表”和“编辑姓名”

## 风险与防护

### 风险 1：历史数据被新机构误看到

防护：

- 所有历史数据统一归属 `星润Starain`
- 所有接口统一走 actor 过滤查询
- 为关键跨机构场景补回归测试

### 风险 2：咨询记录 CSV 迁移丢数据

防护：

- 迁移前保留原 CSV
- 迁移脚本按“读取 CSV -> 写入 SQLite -> 校验记录数”执行
- 首次迁移后仍保留原文件，不立即删除

### 风险 3：已有接口继续绕过机构过滤

防护：

- 不只修列表页，详情和写接口也做机构校验
- 通过测试覆盖 `owner/admin/member/super_owner` 的跨机构访问场景

## 测试策略

### 后端

新增回归测试覆盖：

- `owner` 只能看到本机构成员列表
- `owner` 只能看到本机构待审批注册请求
- `owner/admin/member` 无法访问其他机构班级、课节、咨询记录
- `super_owner` 可以看到所有机构与所有机构成员
- `super_owner` 能看到已注册机构列表
- `owner` 可编辑本机构 `admin/member` 姓名
- `owner` 不可编辑其他机构成员姓名
- `owner` 不可编辑 `owner/super_owner`

### 前端

新增回归测试覆盖：

- `ApprovalPage` 在超级管理员视角显示“已注册机构”区块
- 成员卡片存在“编辑姓名”入口
- 成功/失败状态能正确回显

## 验收标准

- `Test School` 登录后看不到 `星润Starain` 的成员、班级、课节、咨询、错题
- `星润Starain` 的历史数据仍可被超级管理员与星润机构成员正常访问
- 超级管理员能在审批页看到已注册机构列表
- 机构负责人可在审批页修改本机构成员姓名
- 超级管理员默认保留跨机构可见能力
