# 班级管理卡片收纳与命名统一设计

## 背景

当前 `班级管理` 已经作为独立左侧 tab 上线，但页面仍保留第一版后台化组织方式：

- 班级列表信息过长，单卡片信息密度过高
- `成员班级分配` 仍作为页面底部独立大区块存在，导致整页明显过长
- 班级资料中仍要求填写 `teacher_email`，不符合当前业务实际
- 班级名称格式缺少统一约束，容易出现 `6年级2班 / 六年级二班 / 六年2班` 混用

用户已经明确新的业务约束：系统里的“用户”就是老师，因此班级管理页应围绕“班级资料 + 班级内老师分配”组织，不需要单独的成员视角或老师邮箱录入。

## 本次目标

- 去掉班级录入中的“负责老师邮箱”字段
- 将班级列表改为更紧凑、可收纳的卡片式管理视图
- 将“班级老师分配”收回到每个班级卡片内，不再保留页面底部独立大区块
- 统一班级名称格式，减少汉字与阿拉伯数字混用带来的视觉噪音

## 本次明确不做

- 不调整 `owner / admin / member` 权限模型
- 不新增数据库表
- 不删除数据库中的 `teacher_email` 列
- 不对历史所有班级名称做一次性批量迁移
- 不新增批量导入班级、批量分配老师、拖拽排序等扩展能力

## 推荐方案

采用“单展开卡片式班级管理”方案。

页面默认只展示紧凑班级卡片摘要，每次仅允许展开一个班级卡片。展开后，该卡片内部同时承载：

- 班级基本信息编辑
- 班级老师分配

这样做的原因：

- 能直接解决“班级列表太长”的问题
- 将老师分配与班级本体收回到同一上下文中，减少来回扫视和滚动
- 保持现有数据模型与权限模型不变，改造风险主要集中在前端结构层

## 页面结构

## 1. 页面头部

保留当前页面标题与说明，但文案从“成员班级分配”改为“班级老师分配”语义。

建议说明文案：

- 在这里维护机构班级资料，并直接在对应班级内完成老师分配。

## 2. 班级卡片列表

页面主体改为班级卡片列表，不再在页面下方追加独立的全局分配区。

每张卡片默认收起，仅展示摘要信息：

- 班级名称
- 科目
- 负责老师
- 已分配老师数量
- `展开管理` 按钮

推荐卡片文案：

- 负责老师：`{teacher_name}` 或 `未填写负责老师`
- 已分配：`{count} 位老师`

### 收纳规则

- 默认只允许同时展开 1 张卡片
- 打开新卡片时，自动收起当前已展开卡片
- 保存或分配成功后，不强制自动收起，避免用户连续维护时反复展开

## 3. 卡片展开态

展开后的班级卡片分为两块：

### 基本信息

字段收敛为：

- 班级名称
- 科目
- 负责老师

删除字段：

- 负责老师邮箱

编辑态按钮：

- 保存
- 删除班级（仅编辑已有班级时显示）

### 班级老师分配

该区块直接放在当前班级卡片内部，不再单独存在于页面底部。

展示形式：

- 搜索输入框，用于按老师姓名过滤
- 老师勾选列表

交互规则：

- 勾选代表该老师属于当前班级
- 取消勾选代表将该老师移出当前班级
- 勾选操作保持当前页面已有的“即时保存”模式
- 保存中锁定当前班级卡片内相关控件，避免并发覆盖
- 分配失败时仅回滚当前班级的老师选择状态，不影响其他卡片

## 命名统一规则

本次统一采用：

- 年级使用汉字
- 班级序号使用阿拉伯数字

规范格式：

- `六年级 2 班`
- `初一 3 班`
- `高二 1 班`

### 标准化策略

- 新建班级时，前端在提交前对班级名称做一次轻量标准化
- 编辑班级时，若用户修改名称，也按同样规则标准化后保存
- 旧数据不做全量离线清洗；只有新建或编辑过的班级才会收敛到新格式

### 本次标准化边界

本次不引入复杂名称解析器，不尝试覆盖所有自然语言输入，只覆盖当前最常见的学校命名写法，例如：

- `6年级2班`
- `六年级二班`
- `六年2班`

统一输出为：

- `六年级 2 班`

如果输入完全不符合规则，则保留用户原始输入，不做强制改写。

## 数据与接口策略

## 1. 数据模型

继续复用现有模型：

- `classes`
- `user_classes`

不新增新表。

## 2. `teacher_email` 兼容策略

- 数据库中的 `teacher_email` 列暂时保留
- 后端 `POST /api/classes` 与 `PUT /api/classes/<id>` 继续兼容该字段
- 前端不再展示、不再要求填写、不再主动提交非空值

这样可以避免为了一个已弃用字段增加数据库迁移风险。

## 3. 老师分配接口

继续复用现有用户班级分配接口：

- `GET /api/admin/users`
- `GET /api/admin/users/<id>/classes`
- `PUT /api/admin/users/<id>/classes`

本次只改变前端组织方式，不改变接口权限。

## 权限与展示边界

- `owner` 与 `admin` 均可见 `班级管理`
- `owner` 与 `admin` 均可维护班级资料并分配班级老师
- `member` 仍不可见 `班级管理`
- 本页不承担角色升降级
- 本页中的“老师”本质上就是当前系统中的已激活用户

## 测试策略

## 前端

需要新增或调整源码级测试，覆盖：

- 不再出现老师邮箱输入与邮箱展示
- 页面不再保留底部独立“成员班级分配”大区块
- `ClassManagementPage` 内存在卡片展开式结构
- 班级老师分配逻辑位于班级卡片内部
- 命名标准化辅助逻辑存在，并覆盖常见输入样例

## 后端

现有班级 CRUD 与用户班级分配权限测试继续保留。

本次不因为前端去掉邮箱输入而新增数据库迁移测试；接口兼容即可。

## 风险与控制

主要风险在前端状态组织，而非后端数据层：

- 卡片展开/收起状态
- 卡片内编辑状态
- 卡片内老师分配即时保存状态

控制策略：

- 每次只展开一个卡片，降低并发状态数量
- 基本信息保存与老师分配都限制在当前卡片作用域内
- 继续沿用现有异步锁与回滚保护，避免旧请求覆盖新状态

## 预期结果

改造完成后，`班级管理` 页将从“长页面 + 底部分配区”的后台堆叠结构，变为“紧凑班级卡片 + 单卡片内管理”的组织方式。

最终收益：

- 页面更短，更易浏览
- 班级与老师分配关系更直观
- 不再要求填写无业务价值的老师邮箱
- 班级命名风格逐步统一
