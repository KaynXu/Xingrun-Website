# 班级管理与班级分配设计

## 背景

当前后台已经具备班级基础数据模型与旧版班级 CRUD 能力，也已经有一段“成员班级分配”的半成品逻辑混在账号审批页中，但入口和职责仍然混乱：

- 左侧导航没有独立的班级管理入口
- `账号审批` 页面同时承担审批和组织配置，信息密度过高
- `admin` 还不能正式进入班级管理流
- 班级分配与班级维护分散，用户需要在不同位置来回找

本次目标是把班级相关操作提升为正式后台模块，形成一个清晰的左侧 `班级管理` tab，并把成员班级分配整合进去。

## 本次目标

- 左侧新增独立 tab：`班级管理`
- 将现有审批页中的 `班级分配` 抽离到 `班级管理`
- 在 `班级管理` 页面中同时提供：
  - 班级列表
  - 新增班级
  - 编辑班级
  - 删除班级
  - 成员班级分配
- `owner` 与 `admin` 都可以进入 `班级管理`
- `owner` 与 `admin` 都可以给成员分配班级
- `账号审批` 页面回归只处理审批，不再承担班级管理职责

## 本次明确不做

- 不新增新的数据库表
- 不新增班级归档、批量导入、批量分配
- 不新增按成员搜索、按班级筛选成员等扩展工具
- 不把班级管理做成独立路由系统或多页流程
- 不在 `班级管理` 页面内做角色升降级
- 不调整课程日历页的信息结构

## 方案概览

采用“独立班级管理页 + 审批页职责收缩”的方案。

系统结构调整如下：

- 左侧导航新增 `班级管理`
- `账号审批` 页面只保留：
  - 当前 owner 信息
  - 待审批申请队列
  - 审批通过 / 拒绝
- `班级管理` 页面统一承接：
  - 班级 CRUD
  - 成员班级分配

这样做的原因：

- 审批是一次性组织入口动作，班级管理是日常高频配置动作，两者节奏不同
- 现有代码中班级分配已经存在，拆出独立页比继续堆在审批页里更容易维护
- 后续若增加班级状态、班级周报、班级筛选等能力，`班级管理` 会是自然扩展位

## 角色与权限

### owner

- 可见 `账号审批`
- 可见 `班级管理`
- 可新增 / 编辑 / 删除班级
- 可给任意成员分配班级
- 可升降级成员角色

### admin

- 不可见 `账号审批`
- 可见 `班级管理`
- 可新增 / 编辑 / 删除班级
- 可给任意成员分配班级
- 不可升降级成员角色

### member

- 不可见 `账号审批`
- 不可见 `班级管理`
- 仍只能访问现有普通工作台功能

## 页面设计

### 左侧导航

在现有工作台导航中新增 `班级管理` 项，位置与现有后台管理项同级。

可见性规则：

- `owner` 显示
- `admin` 显示
- `member` 隐藏

`账号审批` 的可见性继续保持仅 `owner`。

## 班级管理页

页面分为两大区块。

### 1. 班级列表与编辑区

用途：维护机构内的班级资料。

布局：

- 左侧为班级列表卡片区
- 右侧为班级表单区

班级列表卡片展示字段：

- 班级名称
- 学科
- 年级
- 教师姓名
- 教师邮箱
- 关联课程数

交互规则：

- 默认显示全部班级
- 点击某个班级卡片，右侧表单进入编辑态
- 点击 `新建班级`，右侧表单进入新建态
- 编辑态显示 `删除班级` 按钮
- 删除前要求二次确认
- 保存成功后刷新班级列表
- 保存失败时保留当前输入，不清空表单

表单字段维持现有班级模型：

- `name`
- `subject`
- `grade`
- `teacher_name`
- `teacher_email`

### 2. 成员班级分配区

用途：为成员指定可访问的班级。

展示形式：

- 以成员为行
- 每行展示：
  - 成员姓名
  - 所属机构
  - 角色 badge
  - 班级勾选组

交互规则：

- `owner` 和 `admin` 都可以勾选并保存
- 仍采用当前已存在的 checkbox 勾选方式，降低改造成本
- 保存按用户逐行进行
- 某一行保存中时，仅锁定该用户这一行
- 若保存失败，前端回滚到保存前的班级勾选状态
- 若当前没有班级，展示 `请先创建班级`
- 若当前没有成员，展示空态

角色展示规则：

- 显示角色标签：`最高权限账号 / 管理员 / 机构成员`
- 不在本页提供角色升降级按钮

## 账号审批页调整

`账号审批` 页面删除 `班级分配` 区块，仅保留审批相关内容：

- 当前 owner 账号信息
- 待审批数量
- 待审批申请列表
- 通过 / 拒绝操作

角色切换按钮仍然只属于 owner 管理能力，但本次不放在 `班级管理` 页面中承载，避免班级页与账号治理页混在一起。

## 数据与接口设计

继续复用现有数据模型：

- `classes`
- `user_classes`

不新增新表，不调整当前班级字段结构。

## 保留接口

- `GET /api/classes`
- `GET /api/admin/users`
- `GET /api/admin/users/<id>/classes`
- `PUT /api/admin/users/<id>/classes`
- `PUT /api/admin/users/<id>/role`

## 新增或补齐接口

- `POST /api/classes`
- `PUT /api/classes/<id>`
- `DELETE /api/classes/<id>`

## 权限规则

### 班级列表读取

- `GET /api/classes`
  - 任意已登录用户都可读，保持当前行为

### 班级管理写接口

- `POST /api/classes`
  - `owner` 与 `admin`
- `PUT /api/classes/<id>`
  - `owner` 与 `admin`
- `DELETE /api/classes/<id>`
  - `owner` 与 `admin`

### 成员班级分配

- `GET /api/admin/users`
  - `owner` 与 `admin`
- `GET /api/admin/users/<id>/classes`
  - `owner` 与 `admin`
- `PUT /api/admin/users/<id>/classes`
  - `owner` 与 `admin`

### 角色调整

- `PUT /api/admin/users/<id>/role`
  - 仅 `owner`

### 审批相关

- 所有审批接口继续仅 `owner`

## 删除班级语义

删除班级继续沿用旧系统约定：

- 删除 `classes` 表中的班级记录
- 不删除课程记录
- 课程记录失去该班级归属
- `user_classes` 中相关关联应一并失效，不保留悬空分配

## 错误处理

- 班级名称为空：返回 `400`
- 班级不存在：返回 `404`
- 权限不足：返回 `403`
- 分配保存失败：前端回滚到旧值
- 班级新增 / 编辑失败：保留当前输入并显示错误信息

## 前端实现原则

- 保持现有 workspace 深浅色卡片体系，不另起新视觉系统
- 优先复用已有 `workspaceCardClass`、`workspaceSoftCardClass`、按钮样式常量
- 不新建复杂弹窗体系；班级表单优先以页面内右侧编辑区承载
- 尽量抽离当前 `ApprovalPage` 中的分配逻辑，避免复制粘贴两份状态管理

## 测试与验证

至少覆盖以下路径。

### 后端

- owner 可以创建班级
- owner 可以编辑班级
- owner 可以删除班级
- admin 可以创建班级
- admin 可以编辑班级
- admin 可以删除班级
- admin 可以读取成员班级分配
- admin 可以更新成员班级分配
- member 不能调用班级管理写接口
- owner 仍可访问审批接口
- admin 仍不可访问审批接口

### 前端

- 左侧导航出现 `班级管理`
- `owner` 与 `admin` 可见 `班级管理`
- `member` 不可见 `班级管理`
- `账号审批` 页面不再渲染 `班级分配`
- `班级管理` 页面渲染：
  - 班级列表标题
  - 新建 / 编辑表单
  - 成员班级分配区
- `admin` 进入 `班级管理` 时仍可看到并使用班级分配控件
- 角色升降级按钮不出现在 `班级管理` 页面

## 验收标准

完成后应满足：

- owner 登录后可在左侧看到 `账号审批` 与 `班级管理`
- admin 登录后只能看到 `班级管理`，看不到 `账号审批`
- owner 与 admin 都能在 `班级管理` 中新增班级并保存
- owner 与 admin 都能在 `班级管理` 中为成员勾选班级并保存
- 审批页不再显示班级分配内容
- member 登录后不会看到班级管理入口
