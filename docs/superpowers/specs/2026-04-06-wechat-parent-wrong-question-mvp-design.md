# 微信小程序家长错题上传 MVP 设计

## 背景

当前系统已经存在两块与错题相关的能力：

- 网站端 `智能错题` 工作台
  - 面向内部老师与管理者
  - 已具备列表、详情、跟进处理、导出等工作台能力
- 旧小程序错题链路
  - 更偏家长/学生侧使用
  - 已包含拍照、上传、诊断卡、学生自查、错题记录等能力

但两边的集成边界并不理想。当前最痛的问题不是“页面够不够多”，而是：

- 家长侧上传的数据难以天然和网站主数据对齐
- 老师、班级、学生信息经常需要依赖文本匹配或补充映射
- 如果继续试图统一整套旧小程序和网站，会让范围快速失控

这次目标不是重做完整错题系统，而是做一个最轻量、最清晰的微信小程序 MVP，让家长上传的错题能稳定进入网站老师端工作流。

## 目标

- 提供一个真正轻量的微信小程序家长上传入口
- 让家长上传的错题记录直接进入网站现有 `智能错题` 工作台
- 让每条上传记录在创建时就天然带上网站可识别的班级、学生、老师归属
- 支持一个家长绑定多个孩子
- 通过老师发放的邀请码完成绑定，避免自由文本录入带来的映射问题

## 非目标

本期明确不做：

- 不重构旧小程序完整聊天房间能力
- 不要求微信小程序复刻网站 `智能错题` 工作台
- 不做家长端完整错题历史、AI 详细分析、聊天式交互
- 不做网站与旧小程序所有账号体系的一次性合并
- 不依赖文本猜测去匹配老师、班级、学生

## 方案概览

采用“网站主数据 + 微信小程序上传入口”的双端模型：

- 网站继续作为老师、班级、学生、权限的主数据源
- 微信小程序只承担家长身份识别、班级绑定、学生选择、错题图片上传
- 老师继续在网站现有 `智能错题` 页面查看和处理记录

这不是“统一前端”，而是“统一数据主线”。

## 产品决策

### 1. 网站是主数据源

老师、班级、学生的 canonical identity 必须来自网站，而不是来自家长手填文本。

本期设计里：

- 班级 identity 由网站 `classes.id` 定义
- 学生 identity 由网站学生记录的 `student_id` 定义
- 老师 identity 由网站 `users.id` 定义

小程序里看到的名字仅用于展示，真正的数据关联必须依赖 ID。

### 2. 小程序是家长上传入口

微信小程序 MVP 只做一件核心事情：让家长把错题上传进老师工作台。

这意味着小程序优先服务的不是“完整学习闭环”，而是“低阻力上传 + 正确归属 + 立即进入处理队列”。

### 3. 班级邀请码是绑定入口

家长不搜索老师、不手填班级、不手填学生。

绑定流程采用：

- 老师发放班级邀请码
- 家长在微信小程序输入邀请码
- 系统返回该班信息和该班现有学生名单
- 家长从名单里选择自己的孩子完成绑定

这样可确保数据从一开始就和网站主数据对齐。

### 4. 一个家长可以绑定多个“班级里的学生”

因为存在二胎家庭，也存在同一个孩子在不同班级场景下的可能性，本期不把绑定对象定义成“抽象孩子”，而定义成：

- 某班级下的某个学生

因此同一个家长可以拥有多条绑定，例如：

- 班级 A -> 学生小明
- 班级 B -> 学生小明
- 班级 C -> 学生小红

上传时由家长选择本次要关联的那条绑定关系。

### 5. 班级唯一对应老师

本期已确认：

- 一个班级不会同时对应多个任课老师

因此上传流程无需再额外选择老师或学科。老师归属由班级自动带出。

## 核心用户流

### 1. 老师发班级邀请码

老师或机构后台在网站中查看某个班级的邀请码，并发送给家长。

第一版不要求复杂的邀请码管理后台，只要能满足：

- 生成或查看有效邀请码
- 每个邀请码明确归属一个班级
- 邀请码状态可校验

### 2. 家长进入微信小程序并完成身份识别

家长首次进入微信小程序时，系统通过微信登录获取 `openid`，建立或读取家长微信账号记录。

### 3. 家长输入班级邀请码

家长输入老师发来的班级邀请码后，系统返回：

- 班级名称
- 对应老师展示信息
- 该班现有学生名单

若邀请码无效、失效或已停用，直接提示，不进入下一步。

### 4. 家长从学生名单中选择孩子

家长不能手填学生名，只能从网站已有学生名单中选择。

选择完成后建立“家长微信身份 -> 班级 -> 学生”的绑定关系。

### 5. 家长上传错题

家长在首页从已绑定列表中选择本次要上传的“班级里的学生”，然后：

- 拍照或从相册选图
- 可选填一句家长备注
- 提交上传

上传成功后页面只需显示：

- 上传成功
- 已进入老师待处理队列

第一版不要求展示完整 AI 结果页。

### 6. 老师在网站端看到记录

小程序上传成功后，记录直接进入网站现有 `智能错题` 工作台。

老师在网页中查看时，应能直接看到这条记录已具备：

- 机构归属
- 班级归属
- 学生归属
- 老师归属
- 来源为微信小程序

## 数据设计

### 设计原则

- IDs 是事实，名称只是展示
- 绑定关系优先，不依赖事后文本映射
- 上传记录在写入时就完成归属，不做“先裸记录后补关联”
- 网站继续作为 identity truth

### 核心实体

#### 1. 班级主数据

继续复用网站已有班级实体。

关键要求：

- `classes.id` 作为班级主键
- 每个班级明确归属一个老师用户
- 班级归属机构明确

#### 2. 学生主数据

网站需要具备稳定的学生记录，并且学生归属于具体班级。

建议最小字段：

- `id`
- `organization_id`
- `class_id`
- `name`
- `status`
- `created_at`

说明：

- 本期 student identity 必须是结构化记录，而不是只靠名字文本
- 学生可在不同班级下出现为不同绑定关系

#### 3. 家长微信账号

新增 `parent_wechat_accounts`。

建议字段：

- `id`
- `organization_id` 或可空机构字段
- `openid`
- `nickname_snapshot`
- `avatar_url_snapshot`
- `status`
- `created_at`
- `updated_at`

规则：

- `openid` 全局唯一
- 这张表只表示微信家长身份，不直接决定学生归属

#### 4. 班级邀请码

新增 `class_invite_codes`。

建议字段：

- `id`
- `organization_id`
- `class_id`
- `invite_code`
- `status`
- `expires_at`
- `created_by_user_id`
- `created_at`
- `revoked_at`

状态建议：

- `active`
- `expired`
- `revoked`

业务规则：

- 一个班级同一时刻建议只保留一个 `active` 邀请码
- 家长输入邀请码后，只能绑定到对应班级

#### 5. 家长学生绑定关系

新增 `parent_student_bindings`。

这张表的核心含义不是“家长绑定孩子”，而是“家长绑定某班级下的某个学生”。

建议字段：

- `id`
- `organization_id`
- `parent_wechat_account_id`
- `class_id`
- `student_id`
- `teacher_user_id`
- `status`
- `created_at`
- `updated_at`

状态建议：

- `active`
- `inactive`

约束建议：

- 同一 `parent_wechat_account_id + class_id + student_id` 不应重复创建多条 `active`

#### 6. 家长上传错题记录

新增或扩展网站侧 `wrong_question_submissions` 记录模型。

建议最小字段：

- `id`
- `organization_id`
- `source`
- `parent_wechat_account_id`
- `binding_id`
- `class_id`
- `student_id`
- `teacher_user_id`
- `image_url`
- `parent_note`
- `status`
- `created_at`
- `updated_at`

补充字段可逐步扩展：

- `analysis_payload`
- `review_payload`
- `source_snapshot`

规则：

- `source` 固定标识为 `wechat_mp`
- `status` 初始为 `pending`
- 一条记录在创建时就必须拥有完整的班级、学生、老师归属

## API 设计

### 微信小程序接口

#### 1. `POST /api/wechat/login`

用途：

- 微信小程序完成登录
- 用 `openid` 建立或读取家长微信账号

返回：

- 当前家长身份信息
- 是否已存在绑定记录

#### 2. `POST /api/wechat/bind-class`

用途：

- 校验班级邀请码
- 返回对应班级信息与学生名单

请求：

- `invite_code`

返回：

- `class_id`
- `class_name`
- `teacher_user_id`
- `teacher_display_name`
- `students`

#### 3. `POST /api/wechat/bind-student`

用途：

- 家长从学生名单中选择孩子并建立绑定

请求：

- `class_id`
- `student_id`

返回：

- 创建或已存在的绑定记录

#### 4. `GET /api/wechat/bindings`

用途：

- 拉取当前家长已绑定的“班级里的学生”列表

返回项建议包含：

- `binding_id`
- `class_id`
- `class_name`
- `student_id`
- `student_name`
- `teacher_user_id`
- `teacher_display_name`

#### 5. `POST /api/wechat/wrong-questions`

用途：

- 家长上传错题图片

请求建议：

- `binding_id`
- `image`
- `parent_note`

服务端行为：

- 根据 `binding_id` 解析出 `organization_id / class_id / student_id / teacher_user_id`
- 创建一条网站可直接消费的错题记录
- 将来源标记为 `wechat_mp`

返回：

- `record_id`
- `status`

### 网站工作台接口

网站端继续复用现有 `智能错题` 工作台接口族：

- `GET /api/wrong-questions`
- `GET /api/wrong-questions/:id`
- `PUT /api/wrong-questions/:id/review`

但记录模型需要补充或稳定输出以下字段：

- `source`
- `organization_id`
- `class_id`
- `student_id`
- `teacher_user_id`
- `parent_wechat_account_id`

这样网站端无需再依赖自由文本映射去判断归属。

## 微信小程序页面设计

### 1. 进入页

职责：

- 获取微信身份
- 判断是否已有绑定

分支：

- 已有绑定 -> 进入首页
- 无绑定 -> 进入班级绑定页

### 2. 班级绑定页

职责：

- 输入班级邀请码
- 展示班级信息
- 展示该班已有学生名单
- 让家长选择孩子并完成绑定

关键规则：

- 不允许手填学生名
- 一个家长可重复进入本流程，绑定多个“班级里的学生”

### 3. 首页

职责：

- 显示已绑定学生卡片列表
- 选择本次上传对象
- 进入上传页

首页内容保持极轻：

- 已绑定孩子列表
- 当前班级
- 当前老师
- `上传错题` 按钮
- 可选 `添加孩子` 入口

### 4. 上传页

职责：

- 拍照或选图
- 预览图片
- 填写一句可选备注
- 提交上传

成功页文案只需覆盖：

- 上传成功
- 老师稍后可在后台查看

第一版不加复杂历史列表和分析详情。

## 网站侧需要配合的能力

### 1. 班级邀请码能力

网站端需要为班级提供邀请码能力，至少满足：

- 后台可查看当前邀请码
- 后台可重置邀请码
- 邀请码和班级一一对应

这部分可放在班级管理页内，而不必单独做复杂模块。

### 2. 学生主数据能力

网站端需要确保每个班级下存在结构化学生列表。

这意味着：

- 学生不能只作为错题记录中的文本字段存在
- 家长绑定和上传流程必须能读取同一套学生记录

### 3. 错题记录归属稳定化

网站 `智能错题` 页面读取记录时，应优先基于 canonical IDs 展示和筛选：

- `class_id`
- `student_id`
- `teacher_user_id`

快照文字可保留，但不再作为主关联依据。

## 权限与安全

### 家长侧

- 家长只能看到自己已绑定的“班级里的学生”
- 家长只能使用有效邀请码建立绑定
- 家长上传时不能伪造老师、班级、学生归属

因此上传接口不接受自由传入的归属文本作为事实来源，必须通过绑定记录反查。

### 网站老师侧

- 老师仍按网站现有组织和班级权限查看记录
- 网站端仅能看到归属到自己机构范围内的数据

### 邀请码侧

- 邀请码需要可失效
- 邀请码应支持重置
- 邀请码不可暴露超出班级绑定所需的后台信息

## 错误处理

### 班级邀请码错误

场景：

- 邀请码不存在
- 邀请码已过期
- 邀请码已撤销

处理：

- 小程序直接提示邀请码无效
- 不允许进入学生选择

### 学生绑定冲突

场景：

- 重复绑定同一个班级下同一学生

处理：

- 接口返回已存在绑定，前端按成功状态处理即可

### 上传失败

场景：

- 图片上传失败
- 绑定无效
- 服务端创建记录失败

处理：

- 保持错误提示明确
- 不创建“半归属”的脏记录
- 前端支持重试

## 迁移与落地顺序

建议按最小闭环推进：

1. 补齐网站学生主数据与班级邀请码能力
2. 建立家长微信身份与绑定关系表
3. 打通微信小程序登录、邀请码校验、学生绑定
4. 打通家长上传错题记录写入网站主记录流
5. 让网站 `智能错题` 页面读取并展示来自 `wechat_mp` 的新记录

这条顺序可以确保每一步都直接服务最终 MVP，而不是先做大范围重构。

### 后端

- 邀请码校验接口测试
- 学生绑定接口测试
- 多孩绑定测试
- 上传接口归属字段测试
- 权限隔离测试

### 微信小程序

- 首次进入无绑定流程
- 已绑定用户直达首页
- 班级邀请码错误提示
- 多个孩子切换上传
- 上传成功与失败提示

### 网站端

- 新来源 `wechat_mp` 记录能出现在 `智能错题` 列表
- 记录详情显示正确班级、学生、老师
- 老师只能看到自己权限范围内记录

## 未来扩展

本期设计刻意只覆盖最轻闭环。后续可基于同一数据主线继续扩展：

- 家长端上传历史
- 家长端 AI 分析结果页
- 家长端查看老师反馈
- 绑定关系审核或解绑
- 更细的邀请码管理

这些扩展都不应推翻本期主线，因为本期已经把最关键的 identity 对齐问题先解决。

## 结论

这次 MVP 的本质不是“再做一个完整错题小程序”，而是：

- 用微信小程序提供最低摩擦的家长上传入口
- 用网站继续承接老师处理工作台
- 用班级邀请码与结构化学生绑定，让上传数据从创建开始就和网站主数据对齐

只要这条主线成立，后续无论是加家长历史、老师反馈回流，还是扩展更多移动端能力，都会比现在在两套不完全对齐的系统之间硬适配要顺得多。
