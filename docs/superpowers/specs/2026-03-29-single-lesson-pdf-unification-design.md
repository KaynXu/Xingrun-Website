# 单课 PDF 模板统一设计

日期：2026-03-29
仓库：`/Users/ark.mini/Desktop/Xingrun-Review/Xingrun-Summary`
目标分支：`feat/workspace-shell-starain`

## 背景

当前仓库里存在两套单课 PDF 生成实现：

1. 网页与存库主流程调用 `pdf_engine.generate_lesson_pdf(...)`
2. 同事当前确认在使用、且用户认可版式的是 `review_plan_templates/generate_review_pdfs.py`

这导致了一个直接问题：

- 同一份课堂内容，从网页点击生成得到的 PDF，与独立模板工作区生成的 PDF 不是同一种版式。

用户已经明确确认：后续要保留的目标版式，是 `review_plan_templates` 当前生成出来的那种卡片式课后复习计划 PDF，而不是网页当前主入口输出的版本。

## 目标

将“单课 PDF”统一到同一条正式生成链路，使以下入口输出一致：

1. 网页创建单课 PDF
2. CLI / 数据层生成单课 PDF
3. 手工独立生成单课 PDF

统一后，以上三者都应输出与 `review_plan_templates/generate_review_pdfs.py` 当前默认中文版一致的版式与结构。

## 非目标

本次不处理以下内容：

1. 月度 PDF
2. 周度 / 聚合类 PDF
3. 前端页面结构与交互重做
4. 大规模重构所有 PDF 代码

本次只聚焦“单课 PDF 默认生成路径统一”。

## 现状结论

已经确认的事实：

1. `app.py` 中单课生成入口直接调用 `pdf_engine.generate_lesson_pdf(plan, pdf_path)`
2. `lesson_manager.py` 中存库/CLI 单课生成同样直接调用 `pdf_engine.generate_lesson_pdf(...)`
3. `review_plan_templates/generate_review_pdfs.py` 当前仍是一条独立脚本链路，没有被网页默认入口调用
4. 用户确认想要保留的是独立模板链路生成出来的版式

因此，真正要解决的问题不是“调样式”，而是“统一正式入口”。

## 方案对比

### 方案 A：继续让 `pdf_engine.py` 作为唯一实现，人工把同事模板复刻进去

优点：

1. 现有调用点改动小
2. 外部接口基本不变

缺点：

1. 需要把已确认可用的模板再复制一遍
2. 容易再次出现两份实现漂移
3. 后续维护者仍会困惑“到底看哪份模板是准的”

### 方案 B：把主流程改为桥接到 `review_plan_templates`，让它成为唯一单课模板来源

优点：

1. 与用户确认的目标版式完全一致
2. 不再维护两套单课模板实现
3. 后续模板迭代只有一个事实来源

缺点：

1. 需要增加一层 `plan -> review_plan_templates` 的适配
2. 需要补回归 proof，确保网页主流程仍可稳定生成

### 方案 C：把独立模板整体内联进 `app.py` 或 `lesson_manager.py`

优点：

1. 看似直接

缺点：

1. 会把模板逻辑耦合进业务入口
2. 难测、难维护、边界不清晰

### 推荐方案

采用方案 B。

理由：

1. 用户已经确认目标版式来自 `review_plan_templates`
2. 统一事实来源比继续保留两套模板更重要
3. 通过桥接层适配输入，可以最大程度减少对现有业务入口的侵入

## 设计

### 1. 保留 `review_plan_templates` 作为唯一单课模板来源

新增一个可复用的正式函数入口，由主流程直接调用，而不是继续只靠脚本 `main()`：

1. 将 `review_plan_templates` 中现有的文档构建步骤抽出为可导入函数
2. 函数接受“单课复习数据”与输出路径
3. 默认输出与用户确认的中文单课版式一致

这个入口将成为单课 PDF 的唯一版式来源。

### 2. 新增单课数据适配层

当前业务层提供给 PDF 的数据是系统内部 `plan` 结构；`review_plan_templates` 使用的是另一套 lesson/day 数据结构。

因此需要新增单独适配层，职责只有一个：

1. 接收现有 `plan`
2. 生成目标模板所需的数据结构
3. 不负责 Flask、数据库或文件命名

适配层应放在单独模块中，避免把模板拼装逻辑散落在 `app.py` / `lesson_manager.py`。

### 3. 业务入口统一改到桥接层

以下入口都改为调用“适配层 + review_plan_templates 正式入口”：

1. `app.py` 的单课 PDF 生成
2. `lesson_manager.py` 的单课 PDF 生成

这样网页和 CLI/存库就会自动与同事当前模板保持一致。

### 4. 清理旧单课路径

在确认主流程切换成功后：

1. 删除 `pdf_engine.py` 中不再使用的单课 PDF 渲染入口与单课 helper
2. 保留月度 / 非单课 PDF 相关逻辑不动
3. 删除或停用其它仅服务于旧单课版式的遗留入口

清理的原则是：

1. 只清单课旧路径
2. 不碰非单课能力
3. 不保留两个都能用的单课版式，避免以后再次混淆

## 文件边界

预计涉及的文件职责如下：

1. `review_plan_templates/generate_review_pdfs.py`
   - 从脚本型入口整理出可导入的正式生成函数

2. `review_plan_templates/<new adapter module or reusable helper module>`
   - 承接系统 `plan` 到模板数据的结构转换

3. `app.py`
   - 单课 PDF 入口改为调用新的统一生成函数

4. `lesson_manager.py`
   - CLI / 存库单课 PDF 入口改为调用新的统一生成函数

5. `pdf_engine.py`
   - 删除旧的单课模板实现；保留非单课逻辑

6. `tests/`
   - 补回归 proof，锁定默认单课生成已切到新模板

## 数据适配原则

适配层需要满足以下约束：

1. 允许沿用当前 AI 产出的 `plan` 结构，不要求先改 AI 输出
2. 对缺失字段提供最小降级策略，但不能 silently 生成空白/错版 PDF
3. 生成失败要抛出明确错误，让业务入口能提示“PDF 生成失败”
4. 输出版式优先服从用户确认的目标模板，而不是优先保留旧字段命名

## 清理边界

本次“删掉其他的”具体解释为：

1. 删除旧的单课 PDF 生成实现
2. 删除只为旧单课模板服务的 helper / wrapper / dead path
3. 不删除月度 / 聚合 / 非单课 PDF 逻辑

这样既实现“同一”，也不会误伤其他功能。

## 验证标准

以下条件全部满足，才算完成：

1. 从网页主流程生成一份单课 PDF，首屏版式与 `review_plan_templates` 当前独立生成结果一致
2. 从统一后的可导入入口直接生成一份 PDF，结果与独立脚本版式一致
3. `app.py` 与 `lesson_manager.py` 中不再直接依赖旧单课 `pdf_engine.generate_lesson_pdf(...)`
4. 旧单课模板代码已被删除或明确停用
5. 相关后端回归测试通过

## 风险与控制

### 风险 1：当前 `plan` 数据与新模板结构不完全匹配

控制：

1. 先写 proof，锁定最小可生成样本
2. 适配层显式处理字段缺失与默认值

### 风险 2：切换后网页能生成，但版式与独立模板仍不完全一致

控制：

1. 直接用同一渲染函数作为唯一来源
2. 用 PDF 首屏 proof 做对比，不只看“能生成”

### 风险 3：误删仍在使用的非单课 PDF 逻辑

控制：

1. 本次只清理单课旧路径
2. 月度/其他逻辑保留，不纳入本轮删除范围

## 交付结果

完成后仓库应呈现为：

1. 单课 PDF 只有一条正式模板链路
2. 网页、CLI、独立调用输出同一版式
3. 用户确认的“同事那种 PDF”成为默认结果
4. 旧单课模板不再残留为第二套可选实现
