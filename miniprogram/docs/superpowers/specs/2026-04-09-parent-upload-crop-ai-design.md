# 家长上传页拍照裁剪与 AI 框选设计

## 背景

当前小程序家长上传页只有单图选择、预览、备注、提交流程：

- 只能处理 1 张图片
- 没有裁剪能力
- 一张图里如果有多个错题，无法拆成多条上传
- 家长如果连续拍照或一次选择多张，会被当前单图模型卡住

本设计目标是在现有家长上传链路上做最小路径扩展，让家长可以先选图，再在同一页面内完成裁剪、AI 辅助框题、逐题确认，最后统一提交。

## 目标

- 支持家长一次选择多张图片
- 支持家长连续拍照并把新图片追加到当前待上传列表
- 支持同一张原图中框选多个错题
- 支持同页裁剪，不新增独立裁剪页
- 提供 `AI 框选` 按钮，点击后对当前已选全部图片一起发起 AI 题框检测
- AI 结果只作为候选框，家长自己确认、拖动、删除或补加
- 所有最终框选结果统一提交给老师

## 非目标

- 不做“AI 自动判断质量高低”
- 不做“AI 自动提交”
- 不要求 AI 识别成功后才能继续操作
- 不把多张图合并成一条错题记录

## 关键决策

### 1. 页面结构

采用现有 `pages/parent-upload/index` 同页扩展，不新增单独裁剪页。

原因：

- 用户已经确认更偏向同页处理
- 家长从拍照到确认提交的心智路径更短
- 当前项目保留页面较少，继续复用上传页最小侵入

### 2. 多图与连续拍照

支持两种进入方式：

- 一次从相册选择多张
- 多次拍照，把新照片追加到当前上传队列

这里的“连续拍照”按 MVP 解释为：家长在当前上传任务内可以反复追加新照片，而不是拍完一张就丢失前一张。

### 3. 一张图多个错题

一张原图允许存在多个框。

每个最终框单独生成一条错题记录，保持与当前后端“一条记录对应一张上传图片”的模型一致。也就是说：

- 原图 A 可生成错题 1、错题 2、错题 3
- 原图 B 可生成错题 4、错题 5
- 统一提交时本质上是批量触发多次单记录上传

### 4. AI 的角色

AI 是可选辅助，不是主流程。

- 页面提供 `AI 框选` 按钮
- 点击一次后，对当前已选全部图片一起发起检测
- AI 返回每张图的候选框数量和坐标
- 是否准确由家长自己判断

程序只关心技术状态：

- 未开始
- 处理中
- 已返回候选框
- 识别失败
- 返回 0 个框

程序不展示“质量高/低”之类判断。

### 5. 手机端交互

按手机单列布局设计，不使用双栏。

- 顶部：横向缩略图列表，用于直接切换当前图片
- 中部：当前图片的大图裁剪区
- 框本身支持直接拖动位置与四角缩放
- 底部操作保留 3 个：`补加框`、`删除当前`、`AI 框选`
- 底部有统一提交入口

不单独提供“下一张”按钮，因为点击缩略图本身就可以切图。

不单独提供“微调”按钮，因为已有框应直接拖动修改。

## 方案对比

### 方案 A：纯手动框选

所有图片都由家长自己补框和调整。

优点：

- 实现最简单
- 不依赖 AI

缺点：

- 多图、多题场景下操作量偏大

### 方案 B：手动为主 + AI 框选按钮

用户先选图，页面支持手动框；需要时点击 `AI 框选` 对全部图片一起出候选框。

优点：

- 覆盖单图多题、多图、连续拍照
- AI 出错不阻塞主流程
- 改动可控

缺点：

- 需要前后端新增 AI 检测能力和前端状态管理

### 方案 C：默认自动跑 AI

用户一选图就自动发起批量检测。

优点：

- 更自动化

缺点：

- 首屏状态复杂
- 用户可能不理解为什么一上来就在跑识别
- 不符合当前已经确认的按钮触发方式

最终采用方案 B。

## 架构设计

### 前端页面状态

将当前上传页的单图状态扩展为图片队列。

建议核心数据结构：

```js
{
  binding: {...},
  parentNote: '',
  submitting: false,
  selectedImageId: 'img_1',
  imageItems: [
    {
      id: 'img_1',
      localPath: 'wxfile://...',
      aiStatus: 'idle', // idle | running | done | failed | empty
      aiErrorMessage: '',
      boxes: [
        {
          id: 'box_1',
          source: 'ai', // ai | manual
          x: 0.12,
          y: 0.18,
          width: 0.52,
          height: 0.24
        }
      ],
      activeBoxId: 'box_1'
    }
  ]
}
```

说明：

- 框坐标建议按相对比例存储，避免不同预览尺寸下失真
- `selectedImageId` 表示当前正在编辑哪一张
- `boxes` 为空时表示这张图当前还没有任何可提交题框

### 前端组件职责

建议在 `pages/parent-upload` 内拆分逻辑职责，但仍保持最小侵入：

- 图片队列管理：追加图片、切换当前图片、删除图片
- 框管理：新增框、删除框、拖动框、缩放框
- AI 批量调度：对全部图片发起检测并记录每张状态
- 提交编排：把所有最终框生成裁剪图，再逐条调用现有上传接口

如果代码拆分成本过高，首版也可先在页面文件内实现，但逻辑上需要以上边界。

### 后端能力

当前上传接口 `/wechat/parent/wrong-questions` 仍保留，用于最终逐题上传。

需要新增一个 AI 检测接口，职责仅为“返回候选框”，不负责落库错题记录。建议形态：

- `POST /wechat/parent/wrong-question-boxes`

单次请求处理一张图，返回该图候选框列表。前端在点击 `AI 框选` 后对当前全部图片并发发起请求。

这样做的原因：

- 用户观感上是“全部一起跑”
- 技术实现上不必一次 multipart 传多张图
- 可以天然做到每张图独立成功、独立失败、独立重试

为避免手机端卡顿，前端并发数建议限制在 2 到 3。

### AI 模型与调用约束

这部分之前只写了“接 AI”，但首版落地必须把模型和调用边界写清楚，否则前后端会各自猜。

- AI provider 采用 `N1N`
- 默认基线路径为 `https://api.n1n.ai/v1/chat/completions`
- 默认模型使用 `gpt-4o`
- 模型名必须支持通过运行时配置覆盖，不允许前端写死
- 当前服务端建议运行时配置：
  - `N1N_API_KEY`
  - `XR_N1N_BASE_URL`
  - `XR_N1N_MODEL`
- 服务端请求 N1N 时必须显式带上：
  - `Authorization: Bearer ...`
  - `Content-Type: application/json`
  - `User-Agent`
  - `Accept: application/json`

原因：本轮联调已验证，N1N 的 URL 和 key 本身可用，但 Python 直连时如果缺少标准请求头，provider 可能返回 `403 error code: 1010`。因此“标准请求头”不是实现细节，而是本功能的接口契约之一。

如果后续需要切换到 `responses` 接口或其他模型，也必须满足两个前提：

- 先有真实联调验证结果
- 不改变前端 `AI 框选` 的返回协议

也就是说，前端依赖的是“候选框协议”，不是某个具体模型字符串；但服务端首版默认值必须明确，以保证部署时可复现。

## 用户流程

### 主流程

1. 家长进入上传页
2. 选择相册多张，或拍照追加图片
3. 页面展示图片缩略图队列，默认选中第一张
4. 家长可直接手动补框
5. 家长点击 `AI 框选`
6. 前端对全部图片发起 AI 检测
7. 哪张先返回候选框，就先可编辑哪张
8. 家长逐图检查，拖动已有框、删除误框、补加漏框
9. 页面校验每张图至少有 1 个框
10. 家长点击统一提交
11. 前端按框裁剪出结果图，逐条上传到现有错题接口
12. 全部成功后展示成功结果

### AI 相关流程

- `running`：该图正在识别，页面不锁死
- `done`：返回 1 个或多个候选框
- `empty`：返回 0 个框，提示家长手动补框后再提交
- `failed`：识别失败，可手动补框，也可仅重试当前图

## 交互细节

### 缩略图

- 每张图片在顶部显示缩略图
- 点击缩略图切换当前图片
- 缩略图角标显示状态小圆点
  - 蓝色或绿色：已返回候选框
  - 橙色：处理中
  - 红色：失败或需要补框

### 框操作

- 点击框可切换当前框
- 拖动框体可移动位置
- 拖动四角可调整大小
- `补加框` 在当前图上创建一个默认框，再允许家长继续拖动
- `删除当前` 删除当前选中的框

### 统一提交前校验

统一提交前必须拦截以下情况：

- 某张图片 `boxes.length === 0`
- 当前仍有图片处于 `running`

提示内容要明确指出是哪几张图还未完成，而不是只给模糊错误。

## 错误处理

- 选图失败：保留现有页面，不清空已有图片队列
- AI 检测失败：仅影响对应图片
- AI 返回 0 个框：提示家长先手动补框
- 单条上传失败：保留失败项，允许重试未成功项目
- 批量提交中途失败：展示成功数、失败数及失败项所属图片
- AI provider 不可用、超时、鉴权失败或返回非 JSON 时：前端必须提示“AI 框选失败，请手动补框或稍后重试”，不能再暴露“上传返回解析失败”这类底层报错

## 测试策略

### 前端单测

- 追加图片不会覆盖已有图片队列
- 点击缩略图会切换当前图片
- `AI 框选` 会对所有图片发起检测，而不是只对当前图
- AI 返回框会正确写入对应图片
- AI 返回 0 个框会把该图标记为 `empty`
- 统一提交前若存在 0 框图片会被拦截
- 一张图多个框会被编排成多次最终上传

### 前后端集成验证

- 单图单框上传
- 单图多框上传
- 多图多框混合上传
- 某张图 AI 失败但家长手动补框后仍可提交
- 某张图 0 框时统一提交被拦截

### 人工手机验证重点

- 手指拖动框角时不会误触页面滚动
- 缩略图多于 3 张时依然能顺畅横向滑动
- AI 在后台处理中时，当前已返回结果的图片仍可编辑
- 连续拍照追加后，已存在的框和图片不会丢失

## 风险与取舍

- 小程序端实现可拖拽多框裁剪，前端交互复杂度会上升
- AI 检测接口新增后，需要明确响应速度与超时策略
- 如果统一提交时逐条上传过慢，后续可能需要增加批量上传优化，但不在本次首版范围内

## 实施建议

建议分两步：

1. 先打通无 AI 的多图 + 多框 + 同页裁剪
2. 再接入 `AI 框选` 按钮和每图独立状态

这样即使 AI 部分需要更多调试，手动主流程也能先可用。
